# v0.7 closed-loop retail world

DecisionAgentBench v0.7 adds a new deterministic convenience-retail environment in which an
action today changes inventory, cash, observations, and feasible decisions on later simulated
days. It does not replace the frozen v0.1-v0.3 snapshot worlds, and it does not by itself create a
new scored agent task suite. The discriminating tasks built on this world belong to v0.8.

## What closes the loop

Each episode advances through the following ordered daily transitions:

1. receive due purchase orders, including seeded delays and partial fills;
2. age inventory lots and record expiry or cold-chain spoilage;
3. apply store-specific prices, shelf allocation, active promotions, seasonality, and shocks;
4. realize demand, constrained sales, lost sales, and within-category substitution;
5. realize lagged returns and feedback;
6. post auditable cash and gross-profit effects; and
7. persist store-day metrics and operational events.

The next day begins from the state produced by the previous day. Inventory is lot-tracked and FIFO;
orders create liabilities and later receipts; sales reduce inventory and add cash; returns reduce
profit and cash; and spoilage reduces inventory and profit without inventing a cash movement.

## Public and privileged state

Agents may query only the 18 `cl_*` business and audit tables named in the committed
[`data/closed-loop-v0.7-manifest.json`](../data/closed-loop-v0.7-manifest.json). SQL is read-only,
single-statement, table-authorized, and row-bounded. State changes are available only through typed
methods for ordering, pricing, shelf allocation, promotions, and approvals.

The evaluator alone can read `cl_demand_parameters`, `cl_random_draws`, and `cl_metadata`. This
hidden state is used for simulation and diagnostic oracles, never exposed through the agent SQL
surface. Keyed SHA-256 draws make counterfactual randomness independent of action order: the same
seed and action sequence reproduces the same state and ledgers.

## Actions and structured approvals

- `place_order` changes future receipts, cash, availability, spoilage exposure, and lost sales.
- `change_price` is store-specific and changes later demand and unit economics.
- `allocate_shelf` changes capacity and later product visibility.
- `schedule_promotion` changes price response but requires an approved request.
- approval lifecycles are recorded as `approval_required`, `approval_requested`, `approved` or
  `rejected`, followed by `resumed` or `aborted`.

Denied and completed actions remain auditable. Approval prose is never treated as authorization.

## Generator regimes

The default `train_normal` regime includes heterogeneous stores and products, weekly seasonality,
seeded noise, and operational events. Four additional regimes are reserved for out-of-distribution
and stress checks: `heldout_supply_shock`, `heldout_demand_shift`, `heldout_cold_chain`, and
`stress_mixed`. A manifest records the seed, horizon, regime, sensitivity scales, schema, public and
private tables, counts, and canonical initial-state digest.

Generate, validate, and exactly reproduce an episode with:

```bash
decision-agent-bench generate-closed-loop /tmp/dab-v07 --days 28 --regime train_normal
decision-agent-bench validate-closed-loop /tmp/dab-v07/episode.sqlite
decision-agent-bench verify-closed-loop-reference
```

Use a different output directory, or pass `--overwrite` intentionally, when rerunning generation.
Horizons from 14 through 180 simulated days are supported.

## Reference policies and information fairness

| Policy | Information boundary | Leaderboard eligible |
| --- | --- | --- |
| `random` | Public state plus seeded random choices | Yes |
| `fixed_policy` | Public state and fixed thresholds | Yes |
| `reorder_point` | Public inventory and catalog state | Yes |
| `newsvendor` | Public observed sales history and unit economics | Yes |
| `pricing` | Public observed demand and price history | Yes |
| `information_matched` | Public state available to an evaluated agent | Yes |
| `privileged_oracle` | Hidden demand parameters and simulator state | **No** |

The privileged policy is a diagnostic probe, not a fair comparator and not a guaranteed mathematical
upper bound. Inspect the disclosures or execute a policy with:

```bash
decision-agent-bench show-closed-loop-baselines
decision-agent-bench run-closed-loop-baseline /tmp/dab-policy \
  --policy information_matched --days 60 --regime stress_mixed
```

## Causal intervention checks

Four published matched pairs isolate replenishment, pricing, shelf allocation, and promotion
approval. Each pair begins from the same seed, differs in a declared action, and must produce a
different later observable state and realized outcome:

```bash
decision-agent-bench compare-closed-loop /tmp/dab-causal \
  --scenario replenishment --days 14
```

The invariant suite also checks foreign keys, inventory and lot flow, sales identities, shelf and
storage capacity, temporal ordering, cash reconciliation, approval state machines, authorization,
and deterministic replay across multi-week and multi-month stress runs.

## Claim boundary

v0.7 demonstrates an action-sensitive, reproducible synthetic world and model-free policy surface.
It does **not** establish realism for a named retailer, forecast accuracy, task discrimination,
agent quality, or a general long-horizon capability. Public-source grounding and sensitivity are
documented in the [calibration report](v0.7-calibration-sensitivity.md). Discriminating tasks are a
v0.8 gate; branching workflows and human-time horizon validation remain v0.9 gates.
